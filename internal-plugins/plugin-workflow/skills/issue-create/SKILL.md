# 이슈 발행 → 브랜치 · 워크트리

규칙 원본: [`references/workflow-rules.md`](../../references/workflow-rules.md) — 1 · 2 단계

## 1. 타입을 정한다

| 타입 | 언제 |
|---|---|
| `feature` | 플러그인 · 스킬 · 커맨드 · 조항 · 검사를 **추가**한다. 기존 판정을 바꾸는 것도 여기 (MAJOR) |
| `bugfix` | 규칙 · 훅 · 스크립트가 **의도와 다르게** 동작한다 — 잘못 막음, 못 막음, 오류, 로드 실패 |

애매하면 "전에 통과하던 것이 이제 막히는가" 를 본다. 막히면 feature(판정 변경)다.

새 플러그인이 필요해 보이면 먼저 기존 플러그인에 스킬·조항을 더하는 것으로 되는지 본다. 이미 CLI 가 하는 일이면 만들지 않는다.

## 2. 이슈를 발행한다

본문은 이슈 폼(`.github/ISSUE_TEMPLATE/{타입}.yml`)의 **라벨을 `###` 제목으로** 채운다. CLI 는 폼을 그리지 못하므로 같은 구조의 본문을 직접 넘긴다.

| feature 절 | bugfix 절 |
|---|---|
| 대상 플러그인 · 범위 · 왜 필요한가 · 무엇을 추가하나 · 기존 플러그인으로 안 되는 이유 · 예상 버전 등급 · 완료 조건 · 설계 요약 | 대상 플러그인 · 판정 종류 · 무슨 일이 일어났나 · 기대한 것 · 최소 재현 · 환경 · 더 알아야 할 것 |

```bash
gh issue create --title "[feature] 의존성 방향 검사" --label feature --body-file /tmp/issue.md
```

- 설계 문서(`.agent-tasks/`)는 git 에 없다. 링크하지 말고 요점을 붙인다
- bugfix 의 "최소 재현" 은 그대로 TC 가 된다. 명령 한 줄이나 훅 입력 JSON 으로 쓴다
- 라벨 `feature` · `bugfix` 가 저장소에 없으면 만들어야 한다 — **원격 변경이므로 사용자에게 먼저 묻는다**

## 3. 브랜치와 워크트리를 만든다

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/branch-create.sh" feature 12 plugin-dependency
```

- `origin/main` 에서 `feature/12-plugin-dependency` 를 만들고 `.claude/worktrees/12-plugin-dependency` 에 워크트리를 둔다
- slug 는 영문 kebab-case 1 ~ 5 단어. 이슈 제목을 줄인 것이다 (`W-03`)
- 워크트리 세션에서 도는 훅은 **main 의 규칙**이다 (설치 기준이 메인 체크아웃). 워크트리에서 고친 플러그인은 스크립트와 TC 를 직접 돌려 검증하고, 로드 확인은 머지 뒤에 한다

## 하지 않을 것

- 이슈 없이 브랜치를 만들지 않는다 (부트스트랩 예외 한 번뿐 — 규칙 원본 5절)
- `develop` 같은 장기 브랜치를 만들지 않는다
- 라벨 생성 · 이슈 발행을 사용자 확인 없이 처음 하지 않는다 — 원격에 남는다
