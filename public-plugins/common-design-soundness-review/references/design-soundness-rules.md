# 설계 건전성 규칙 (단일 원본)

작업 중에 세운 설계(플랜 모드 계획 · 대화 속 설계안 · 설계 문서)를 구현 전에 **앞뒤가 맞는가** — 근거 · 모순 · 전개 · 플로우 · 요구 적합 — 작성 맥락 없는 검증자가 판정한다. 기계 판정은 [`scripts/design-soundness-validate.sh`](../scripts/design-soundness-validate.sh), 조항의 출처는 [`design-soundness-methods.md`](design-soundness-methods.md), 패턴은 [`design-soundness-patterns.json`](design-soundness-patterns.json).

대상은 소프트웨어 설계(구조 · 플로우 · 결정)다. UI · 시각 디자인은 다루지 않는다.

다루지 않는 것:
- 구현한 코드 변경이 필요한가 · 맞는가 → `common-evidence-review`
- 문서의 경로 · 명령 · 버전이 저장소와 맞는가, 군더더기 → `common-document-slop-review`
- 문서에 단 DOI · arXiv ID 의 실재 → `reference-search`
- 기존 코드에서 설계를 복원해 검토, TLA+ · Alloy 모델 자동 생성

## 1. 대상과 모드

| 설계가 나오는 곳 | 검토 대상 | 강제 |
|---|---|---|
| 플랜 모드 계획 | 계획 파일 (`planFilePath`) | `DD-31` — 검토 없이 나가면 한 번 막는다 |
| 설계 문서 | 쓰거나 고친 문서 | `DD-30` — 검토 없이 끝내면 한 번 되돌린다 |
| 대화 속 설계안 | 스킬이 설계안만 옮긴 임시 파일 | `DD-32` — 설계 요청 뒤 첫 코드 편집에서 알린다 |
| 남이 준 설계 | 사용자가 준 문서 | 없음 |

| 모드 | 언제 | 결과 |
|---|---|---|
| 내 설계 | 이번 세션에서 세운 계획 · 설계안 · 고친 문서 | 판정대로 고치고 재검토 |
| 남의 설계 | 그 밖. 사용자가 경로를 주고 검토를 요청함 | 보고서 — 설계 요약 → 판정 → 설계자에게 물을 질문. 원문을 고치지 않는다 |

## 2. 판정 — AI

### 독립성과 기준

| 조항 | 내용 |
|---|---|
| `DD-01` | 판정은 설계한 문맥 밖의 `design-soundness-reviewer` 가 한다. 설계한 쪽이 자기 설계를 다시 읽는 것은 검토로 치지 않는다 |
| `DD-02` | 검증자에게는 **설계 파일 경로 · 요구 출처 · 질문 목록**만 넘긴다. 대화 속 설계안은 설계안만 임시 파일로 옮긴다. 설계에 이른 대화 · 이유 · "이건 의도한 것" 같은 설명은 넘기지 않는다 |
| `DD-03` | 판정 전에 기준을 정한다. 요구 출처는 이 순서로 찾는다: 훅이 기록한 요청 원문 → 요청이 가리킨 이슈 · 요구 문서 → 설계의 목적 · 문제 절에서 뽑아 사용자에게 확인받은 목록. 아무것도 없으면 `DD-08` · `DD-13` 은 `판정 불가` 다. 뽑은 요구는 "설계에서 추출 · 사용자 확인" 으로 표시한다 |
| `DD-15` | 판정 전에 **설계 요약**을 낸다 — 구성요소, 결정 목록(결정 · 고른 것 · 버린 대안), 플로우 표(단계 · 전이 · 분기), 요구와 결정을 잇는 표. 행마다 인용을 단다. 요약을 만들 수 없는 부분은 그 자체가 `빈 곳` 이다 |

### 관점

검증자 하나가 순서대로 판정한다.

| 조항 | 관점 | 내용 |
|---|---|---|
| `DD-04` | 논증 구조 | 최상위 주장("이 설계는 요구 X 를 채운다")을 하위 주장 · 근거로 쪼갠다. 근거 없는 잎이 `빈 곳` 이다 |
| `DD-05` | 반박 | 핵심 결정마다 그 결정을 무너뜨릴 반박을 2개까지 만들고 설계가 답하는지 본다. "이 설계로 6개월 뒤 실패했다면 원인은" 을 반박 생성 질문으로 쓴다 |
| `DD-06` | 모순 · 용어 | 같은 대상(수치 · 상태 · 책임 주체 · 순서)에 대한 다른 진술, 같은 개념의 다른 이름, 지시 대상이 둘 이상인 지시어 |
| `DD-14` | 전개 | 정의하기 전에 쓴 개념, 앞에 없는 사실 · 요구에서 나온 결론, 뒤를 읽어야 앞을 이해하는 순서 |
| `DD-07` | 플로우 건전성 | 시작에서 닿지 않는 단계, 끝으로 못 가는 단계, 실패 · 타임아웃 · 재시도 분기 없음, 다이어그램과 본문 · 다른 다이어그램끼리 다른 전이 |
| `DD-13` | 플로우 적절성 | 단계마다 기여하는 요구를 잇는다. 기여가 없는 단계는 `빈 곳` 이다. 순서를 바꾸거나 단계를 합쳐도 요구가 채워지면 그 이유를 밝혔는지 본다. 핵심 플로우에 대안과의 비교가 없으면 `빈 곳` 이다. 더 나은 플로우를 새로 설계하지 않는다 |
| `DD-08` | 요구 적합 | 요구를 시나리오(자극 · 환경 · 응답 · 측정)로 놓고 시나리오마다 그것을 채우는 결정을 잇는다. 결정 없는 시나리오는 `빈 곳`, 시나리오 없는 결정은 근거를 묻는다. 한 결정이 품질 속성 둘에 상반되게 미치면 그 트레이드오프를 밝혔는지 본다 |
| `DD-09` | 결정 기록 | 결정마다 고려한 대안 · 고른 이유 · 결과 · 확인 방법이 있는가 |

### 판정과 처리

| 조항 | 내용 |
|---|---|
| `DD-10` | 지적마다 **인용(`파일:줄` 과 발췌)을 먼저** 쓰고 판정한다. 값은 `결함`(인용끼리 앞뒤가 안 맞음) · `빈 곳`(있어야 할 근거 · 결정 · 분기가 없음) · `판정 불가`(기준이 설계 밖에 없음). 지적이 없으면 `문제 없음` 이 정상 결과다 |
| `DD-11` | 영향 없는 지적(문체 · 취향 · "더 좋게")은 쓰지 않는다 |
| `DD-12` | 내 설계면 `결함` · `빈 곳` 을 고치고 고친 부분만 다시 판정한다. 재검토는 2회까지, 남으면 사용자에게 넘긴다. 남의 설계면 고치지 않고 보고서와 **설계자에게 물을 질문**을 낸다. 질문은 "이 설계로 시나리오 S 를 구현하려면 무엇을 해야 하는가" 처럼 설계를 써 보게 하는 형태다 |

## 3. 기계 검사 — 알림

설계 문서를 쓸 때(PostToolUse), 플랜 모드를 나갈 때(`DD-31` 메시지), CLI 로 돈다. 막지 않는다. 같은 파일에서 이미 알린 신호는 다시 알리지 않는다.

설계 문서는 아래 중 하나다.
- 경로에 `adr/` · `adrs/` · `decisions/` · `rfc/` · `rfcs/` · `design/` · `designs/` 디렉터리가 있거나 파일명이 `*-design.md` · `*-rfc.md` 인 `.md` · `.mdx` · `.markdown`
- 첫 20줄에 `<!-- design-document -->` 가 있는 파일
- `DESIGN_SOUNDNESS_PATHS` 를 주면 기본 경로 대신 그 글롭 목록(쉼표 구분, 프로젝트 기준 경로)을 쓴다. 표지는 그대로 본다

절은 제목 줄(`##` 이하. 첫 `#` 제목은 문서 제목이라 절로 치지 않는다)이 [`design-soundness-patterns.json`](design-soundness-patterns.json) 의 키워드에 맞는 곳과 그 하위 제목이다. 영어 키워드는 단어 경계로, 한국어 키워드는 부분 문자열로 찾는다. 용어와 결정 단어가 같이 든 제목(`## 설계 용어`)은 용어 절이다.

| 조항 | 신호 | 판정 |
|---|---|---|
| `DD-20` | 필수 절 누락 | 제목 줄에서 절 키워드를 찾는다. 설계 문서는 6절(문제 · 목적 / 요구 · 품질 속성 / 결정 / 고려한 대안 / 위험 · 트레이드오프 / 확인 방법), 계획은 4절(목표 · 요구 / 접근 · 결정 / 위험 / 확인 방법) |
| `DD-21` | 플로우 막힘 | mermaid `stateDiagram` · `stateDiagram-v2` · `flowchart` · `graph` 의 간선(`-->` · `--->` · `-.->` · `==>` · `<-->`, `|라벨|` · `-- 라벨 -->` · `-. 라벨 .->` 포함)으로 그래프를 만든다. 노드 라벨(`[…]` · `(…)` · `{…}` · 따옴표) 안의 글자와 줄 끝 `;` 는 노드로 치지 않는다. 다이어그램마다 따로 본다. 상태도에 `[*]` 시작이 있으면 거기서 닿지 않는 상태, `[*]` 종료가 있으면 거기로 못 가는 상태를 알린다. 종료가 없는 상태도와 flowchart 는 나가는 간선이 없는 단계를 끝으로 보고, 끝으로 못 가는 단계(출구 없는 루프)를 알린다 |
| `DD-22` | 요구 ID 추적 | 요구 ID(`DESIGN_SOUNDNESS_REQUIREMENT_ID`, 기본 `(R|FR|NFR|QA|REQ)-[0-9]+`, 앞에 영숫자가 붙으면 다른 ID 다)가 결정 절 밖에서 줄 머리(표 첫 칸 · 목록 · 제목)에 처음 나오면 정의다. 정의가 하나라도 있을 때, 정의 없이 참조된 ID 와 결정 절에서 한 번도 참조되지 않은 정의를 알린다 |
| `DD-23` | 측정 기준 없는 품질 요구 | 요구 절 안에서 품질 형용사가 있고 숫자가 없는 줄 (요구 ID 의 숫자는 세지 않는다) |
| `DD-24` | 정의 전 용어 사용 | 용어 절이 있고 결정 절이 없거나 결정 절보다 앞에 있을 때만 본다 — 문서 끝의 용어집은 참고용이다. 용어 절의 표 첫 칸 · `- **용어**` 로 정의된 두 바이트 이상의 용어가 정의 줄보다 앞의 본문 · 제목에서 쓰이면 알린다. 조사가 붙는 한국어라 부분 문자열로 찾는다(`주문` 은 `주문서` 에도 맞는다). 용어 절 안의 줄은 보지 않는다 |

보지 않는 곳: 프런트매터 · 인용(`>`) · HTML 주석(줄 안의 주석은 주석만 지운다) · mermaid 가 아닌 코드 펜스. 의도한 줄이면 그 줄이나 바로 윗줄에 `<!-- design-soundness-ignore -->` 를 둔다.

`DD-21` 이 보지 않는 것: 중첩 상태(`state X { … }`) 안팎의 구분, `--x` · `--o` · `---`(화살표 없는 연결) 간선, 간선 없이 선언만 된 노드.

## 4. 게이트

`DESIGN_SOUNDNESS_GATE=0` 이면 세 게이트를 모두 끈다. 기계 검사 알림은 그대로 돈다.

### `DD-30` 설계 문서 게이트 — Stop

한 요청에서 프로젝트 안 설계 문서를 바꾼 줄이 3줄 이상인데 `design-soundness-reviewer` 가 돌지 않았으면 종료를 **한 번** 되돌린다.

- 바꾼 줄은 편집마다 비어 있지 않은 줄 수를 고치기 전 · 후 중 큰 쪽으로 센다
- 되돌림 메시지에 고친 문서 · 요청 기록 경로 · 문서의 `DD-20` ~ `DD-24` 신호를 넣는다
- 이 훅이 되돌린 뒤의 종료(`stop_hook_active`)는 막지 않고 기록을 지운다. 다른 훅이 되돌렸을 뿐이면 그대로 판정한다
- 검토 뒤에 또 고치면 그 뒤 편집만 다시 센다
- 판정할 설계가 없는 편집(오타 · 링크)이면 이유를 한 줄로 말하고 끝내면 된다

### `DD-31` 플랜 모드 게이트 — PreToolUse `ExitPlanMode`

이번 요청에서 `design-soundness-reviewer` 가 돌지 않았으면 exit 2 로 막고, stderr 에 계획 파일 · 요청 기록 · 계획의 `DD-20` ~ `DD-24` 신호를 넣는다.

- 같은 계획(본문 cksum 이 같음)으로 다시 나가면 막지 않는다
- 계획 본문은 `tool_input.plan`, 없으면 `tool_input.planFilePath` 의 파일을 읽는다. 둘 다 없으면 통과한다. 신호는 그 본문을 기록 디렉터리에 쓴 사본으로 본다
- `DESIGN_SOUNDNESS_PLAN_GATE=0` 이면 이 게이트만 끈다

### `DD-32` 설계 뒤 첫 코드 편집 — PostToolUse

요청 원문에 설계 신호어(`design_request_re`)가 있고 검토가 돌지 않은 채 프로젝트 안 코드 · 설정을 처음 고치면 **알린다**. 요청마다 한 번이다. 막지 않는다 — 대화에서 어디까지가 설계인지 기계가 가르지 못한다.

### 기록

`UserPromptSubmit` 이 요청 원문을 기록하고(`DD-03` 의 첫 요구 출처), 앞 요청의 기록을 지운다. 기록은 `CLAUDE_PLUGIN_DATA`(없으면 임시 디렉터리)의 세션별 파일이다.
