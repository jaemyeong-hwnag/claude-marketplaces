# 설계 건전성 리뷰

규칙 원본: [`references/design-soundness-rules.md`](../../references/design-soundness-rules.md)
근거: [`references/design-soundness-methods.md`](../../references/design-soundness-methods.md)

설계한 문맥에서 다시 읽는 것은 검토가 아니다 (`DD-01`). 이 스킬은 설계를 파일로 정하고, 판정할 것을 **결론 없이** 정리해 `design-soundness-reviewer` 에게 넘기고, 받은 판정대로 처리한다. UI · 시각 디자인은 대상이 아니다.

## 1. 대상과 모드

| 상황 | 대상 파일 | 모드 |
|---|---|---|
| 플랜 모드 게이트(`DD-31`)가 막았다 | 메시지의 계획 파일 | 내 설계 |
| 설계 문서 게이트(`DD-30`)가 되돌렸다 | 메시지의 설계 문서 | 내 설계 |
| 대화로 설계안을 냈다 · `DD-32` 알림 | 설계안을 **그대로** 옮긴 임시 파일 (`${CLAUDE_PLUGIN_DATA}` 또는 임시 디렉터리의 `design-<시각>.md`). 설계안에 없는 설명 · 이유를 덧붙이지 않는다 | 내 설계 |
| 사용자가 경로를 주고 검토를 요청했다 | 그 파일 | 남의 설계 |

계획 · 설계안을 아직 안 냈으면 먼저 설계를 끝내고 이 스킬로 온다.

## 2. 요구 출처를 정한다 (`DD-03`)

1. 게이트 메시지의 요청 기록 파일 — 사용자 요청 원문이다
2. 없으면 대화에서 사용자가 쓴 요청을 고치지 않고 옮긴다. 요청이 이슈 · 요구 문서를 가리키면 그것도 넣는다
3. 그래도 요구가 없으면 설계의 목적 · 문제 절에서 요구 후보를 뽑아 **사용자에게 한 번 확인받는다**. 확인받은 목록에 "설계에서 추출 · 사용자 확인" 을 붙인다
4. 사용자가 확인하지 않으면 요구 출처 없이 넘긴다 — 적합도는 `판정 불가` 가 된다

## 3. 기계 신호를 받는다

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/design-soundness-validate.sh" <설계 파일>          # 설계 문서
"${CLAUDE_PLUGIN_ROOT}/scripts/design-soundness-validate.sh" --plan <계획 파일>   # 계획
```

신호는 후보다. 질문으로 바꿔 넘긴다.

## 4. 넘길 것을 만든다 (`DD-02`)

검증자에게는 셋만 넘긴다.

1. **설계 파일 경로**
2. **요구 출처** — 파일 경로 또는 원문
3. **질문 목록** — 기계 신호와 내가 한 주장을 **결론이 들어가지 않은 열린 질문**으로 바꾼다

| 내 주장 · 신호 | 넘길 질문 |
|---|---|
| 재시도로 결제 실패를 다 흡수한다 | 결제 실패의 종류마다 이 설계는 어떤 경로로 끝나는가? |
| 캐시를 넣어 응답 요구를 채운다 | 응답 시간 요구를 채우는 결정은 무엇이고, 그 결정이 다른 요구에 주는 영향은? |
| `DD-21` 끝으로 못 가는 단계 — 재시도 | `재시도` 상태에서 나가는 전이는 무엇이고 언제 일어나는가? |
| `DD-20` 필수 절 없음 — 고려한 대안 | 핵심 결정마다 버린 대안과 버린 이유는 어디에 있는가? |

넘기지 않는 것: 설계에 이른 대화, 내가 왜 그렇게 했는지, 무엇이 맞다고 보는지, 예/아니오 질문 ("이 플로우 맞지?").

## 5. 검증자를 부른다

`design-soundness-reviewer` 에이전트를 부른다. 프롬프트는 아래 형식만 쓴다.

```
설계 파일: <경로>
모드: 내 설계 | 남의 설계

요구 출처:
<경로 또는 원문>

질문:
1. <열린 질문>
```

에이전트를 쓸 수 없는 환경이면 검토하지 못한 것이다. 스스로 다시 읽고 통과시키지 않는다. 사용자에게 `판정 불가` 로 알린다.

## 6. 처리한다 (`DD-12`)

| 판정 | 내 설계 | 남의 설계 |
|---|---|---|
| `결함` | 고친다 | 보고서에 넣고 질문으로 만든다 |
| `빈 곳` | 채운다 — 채울 근거가 없으면 사용자에게 묻는다 | 보고서에 넣고 질문으로 만든다 |
| `판정 불가` | 무엇이 있으면 판정할 수 있는지 사용자에게 알린다 | 보고서에 그대로 둔다 |

- 내 설계는 고친 부분만 다시 검증자에게 넘긴다. 재검토는 2회까지다. 남으면 사용자에게 넘긴다
- 플랜 모드면 계획 파일을 고친 뒤 다시 플랜 모드를 나간다
- 남의 설계는 원문을 고치지 않는다. 보고서는 설계 요약 → 판정 → 설계자에게 물을 질문 순서다. 파일로 낼 때는 프로젝트의 문서 위치 규약을 따른다
- 설계에 저장소 사실 주장 · 인용이 많으면 `common-document-slop-review` · `reference-search` 를 같이 쓰라고 알린다 (설치돼 있을 때)

## 7. 보고한다

```
설계 건전성 리뷰 — <대상> (<모드>)
- 요구 출처: <…>
- 결함 N · 빈 곳 N · 판정 불가 N
- 고친 것: <위치> <관점> <무엇을 어떻게>     (내 설계)
- 설계자에게 물을 질문: N개                    (남의 설계)
- 미확인: <판정 불가 항목> — <필요한 것>
```

## 지키지 않을 것

- 검증자가 문제를 못 찾았다고 설계가 맞다고 확인된 것은 아니다. `판정 불가` 가 남으면 `미확인` 이다.
- 리뷰를 핑계로 요청 밖의 설계를 바꾸지 않는다.
