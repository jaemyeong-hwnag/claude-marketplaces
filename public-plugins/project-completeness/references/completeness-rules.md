# 완성도 규칙 (단일 원본)

프로젝트가 **서비스로서 갖출 것을 갖췄는가**를 재고 메우는 규칙. 세 스킬(`completeness-review` · `completeness-apply` · `service-health-review`)과 `scripts/project-completeness.sh` 가 이 문서를 따른다.

| 무엇 | 어디 |
|---|---|
| 항목 69개 · 핵심 표시 · 측정 방식 · 프로젝트 타입별 N/A · 등급 경계 | `completeness-checklist.json` |
| 서비스 건강도 지표 18개 · 기준 | `service-health-metrics.json` |
| 도입 레시피 | `recipe-common.md` · `recipe-node.md` · `recipe-python.md` · `recipe-go.md` · `recipe-ops.md` · `recipe-service.md` |
| 탐지 · 범위 · 채점 · 지표 판정 · 레시피 조회 | `scripts/project-completeness.sh` |

## 1. 여섯 질문

"완성도" 를 답할 수 있는 질문으로 나눈다. 대부분의 팀은 1 ~ 3 만 잰다. **5 가 이 플러그인의 존재 이유다.**

| # | 질문 | 축 (`id` 접두사) | ISO/IEC 25010 |
|---|---|---|---|
| 1 | 코드가 잘 쓰였나 | `code` | Maintainability |
| 2 | 기능이 다 있고 안 터지나 | `test` · `security` | Functional Suitability · Security |
| 3 | 빠른가 | `perf` | Performance Efficiency |
| 4 | 쓸 만한가 | `ux` | Interaction Capability |
| 5 | 서비스로서 완성됐나 | `service` · `ops` | Quality in Use · Reliability |
| 6 | 팀이 지속 가능하게 굴리나 | `product` | Quality in Use |

항목 id 는 `{축}.{slug}` 로 고정한다 (`security.secret-scan`). 번호를 쓰지 않는다 — 항목이 늘면 N/A · 핵심 목록이 어긋난다.

## 2. 판정 원칙

| 조항 | 내용 |
|---|---|
| `Q-01` | **추측 통과 금지.** 파일 · 설정 · 실행 결과 · 사용자 답으로 확인한 것만 통과다. 확인하지 못한 것은 미통과 + "확인 필요" |
| `Q-02` | `detect` 의 `passed` · `failed` 는 그대로 쓴다. `hints` 는 판정이 아니다 — 코드가 구현한 것인지 데이터가 언급한 것인지 모른다. **직접 읽거나 물어서** 확인한 뒤에만 통과로 올린다 |
| `Q-03` | 위험도와 실천 범위는 다른 질문이다. **범위가 좁은 것과 위험한 것은 다르다** — 핵심을 갖춘 라이브러리는 범위 20% 여도 위험하지 않다. 등급 하나로 "위험하다" 고 말하지 않는다 |
| `Q-04` | N/A 는 **전제가 구조적으로 없을 때만** 쓴다. 프로젝트 타입의 N/A 는 자동이고, 그 밖은 사용자 선언 N/A 로 따로 표시한다. **"우리는 안 해서" 는 N/A 가 아니라 미통과다** |
| `Q-05` | 있는가와 잘 되는가를 섞지 않는다. 체크리스트는 장치의 존재를, 건강도는 실측 수치를 본다. SLO 문서가 있어도 준수율 95% 면 SLO 가 아니라 희망사항이다 |
| `Q-06` | 재지 않은 지표는 통과가 아니라 **미측정**이다. 모르는 값을 추정해 넣지 않는다 |
| `Q-07` | 한 번에 한 축. 진단 뒤 제안은 **가장 비어 있는 축 하나**만 — 여러 축을 동시에 고치라고 하지 않는다 |

### 핵심 항목 — 없으면 실제로 위험한 것

`code.lint-ci` · `code.quality-gate` · `test.e2e-flow` · `security.secret-scan` · `security.critical-vulnerability` · `security.dependency-update` · `ops.slo` · `ops.oncall-runbook` · `ops.rollback` · `service.admin-tool` · `service.backup-restore` · `service.render-smoke`

핵심 통과율로 위험도(🟢 안전 · 🟡 주의 · 🟠 취약 · 🔴 위험)를, 적용 항목 전체 통과율로 실천 범위(🏆 포괄 ~ ⬜ 최소)를 낸다.

### 프로젝트 타입

`detect` 가 추론한다. `null` 이면 사용자에게 묻는다.

| 타입 | 추론 근거 |
|---|---|
| `monorepo` | JS 워크스페이스 · pnpm · lerna · turbo · nx. 패키지마다 성격이 달라 N/A 를 일괄로 두지 않는다 — 패키지별로 따로 진단한다 |
| `docs-static` | 마크다운이 소스의 3배 이상, UI · 서버 없음 |
| `cli` | `bin` 엔트리 또는 CLI 프레임워크 (commander · click · cobra · clap · picocli) |
| `library` | 공개 패키지 · UI · 서버 없음. JVM 은 `java-library` · `maven-publish` 에 진입점(`@SpringBootApplication` · `main`)이 없을 때 |
| `fullstack` · `web-frontend` · `backend-api` | UI 프레임워크 · 서버 프레임워크(spring-boot-starter-web 포함) · 컨테이너 |
| `mobile` · `game` · `embedded` · `data` | 추론하지 않는다 — 사용자가 고른다 |

### 서비스 축은 코드만으로 판정할 수 없다

`service` 항목 다수(빈 상태 · 환불 경로 · 백업 복원 · 운영 도구)는 저장소 밖에 답이 있다. `detect` 의 흔적은 **어디를 볼지**만 알려준다. 흔적이 있으면 그 코드를 읽어 동작을 확인하고, 없으면 사용자에게 묻는다. 운영 도구는 별도 저장소일 수 있고, 백업은 존재가 아니라 **복원 성공 이력**이 기준이다.

## 3. 적용 원칙

| 조항 | 내용 |
|---|---|
| `Q-11` | 진단 없이 도구부터 설치하지 않는다. 이미 있는 것을 다시 넣지 않는다 |
| `Q-12` | **리포트 먼저, 차단은 나중에.** 처음 넣는 검사는 CI 를 실패시키지 않는다. 예외 — 시크릿 탐지 · Critical 취약점 |
| `Q-13` | **임계값은 현재 값에서 시작한다.** 커버리지 80% · 번들 100KB 같은 임의의 숫자를 넣지 않는다. 측정값으로 하락만 막고, 목표는 그다음이다 |
| `Q-14` | 기존 파일을 덮어쓰지 않는다. 바꿀 내용을 보여주고 동의를 받는다 |
| `Q-15` | 레시피의 **검증** 명령을 실제로 돌린다. 도구가 안 돌면 롤백한다. 코드에 실제 문제가 있어 실패하면 설정은 남기고 임계값을 현재 값으로 두고 보고한다 |
| `Q-16` | 커밋하지 않는다. 변경 목록을 보고하고 커밋은 사용자가 정한다 |
| `Q-17` | 레시피에 없는 도구를 임의로 설정하지 않는다 — 레시피가 없다고 알린다 |
| `Q-18` | 자동 검사를 넣었다고 수동 항목을 통과시키지 않는다. 자동 접근성 검사는 WCAG 이슈의 30 ~ 40% 만 잡는다 — `ux.a11y-manual` 은 그대로 미통과 |
| `Q-19` | 레거시 전체에 게이트를 걸지 않는다 — 신규 · 변경 코드에만 (Clean as You Code). AI 코드리뷰로 PR 을 차단하지 않는다 |

### 게이트 단계

| 검사 | 처음 | 승격 |
|---|---|---|
| 시크릿 탐지 · Critical/High 취약점 · 타입 · 린트 에러 | 🔴 차단 | - |
| 신규 코드 커버리지 · 성능 · 번들 예산 | 🟡 경고 | 안정화 뒤 차단 |
| 뮤테이션 스코어 | 🟢 리포트 | - |
| AI 리뷰 지적 | 🟢 코멘트 | **차단하지 않는다** — 오탐으로 신뢰가 무너진다 |

### 축 순서

공백이 여럿이면 앞에서부터. 서비스가 이미 프로덕션에 있으면 운영을 2순위로 올린다.

```
보안(시크릿 → SCA → SAST) → 코드(린트 → 타입 → 미사용) → 테스트(커버리지 → 뮤테이션 → E2E)
→ 성능(예산 → 기준선) → 접근성 → 운영
```

운영 축 안은 역전하지 않는다 — 관측성 없는 SLO 는 잴 데이터가 없고, SLO 없는 온콜은 무엇으로 깨울지 모른다.

```
관측성(OpenTelemetry) → SLO · 에러버짓 → 알림 · 온콜 · 런북 → 롤백 수단 → 상태 페이지 → 포스트모템
```

관측성 · 알림은 설정만 하고 동작하지 않아도 에러가 나지 않는다. 트레이스가 백엔드에 닿았는지, 테스트 알림이 담당자 기기까지 갔는지 **눈으로 확인**한다.

## 4. 레시피

모든 레시피는 여섯 칸을 갖는다. 하나라도 빠지면 적용하지 않는다.

| 칸 | 뜻 |
|---|---|
| 메우는 항목 | 항목 id — `recipe <id>` 가 이 칸으로 찾는다 |
| 선행 조건 | 없으면 적용하지 않는다 |
| 설치 | 실제로 실행할 명령 |
| 설정 | 만들거나 고칠 파일과 내용 |
| 검증 | 적용 직후 돌려서 성공을 확인하는 명령 |
| 롤백 | 되돌릴 때 지울 파일 · 의존성 |

- `<앱 주소>` · `<수집기 주소>` 같은 꺾쇠 자리는 대상 프로젝트에서 채운다 (로컬 앱이면 `localhost:<포트>` 의 http 주소)
- 서드파티 CI 액션은 태그가 아니라 커밋 SHA 로 고정한다 — 태그는 옮겨질 수 있다
- 버전이 박힌 레시피는 가장 빨리 낡는다. 설치한 버전의 설정 형식이 다르면(예: golangci-lint v2 가 v1 설정을 거부) 레시피를 억지로 맞추지 말고 사용자에게 알린다
- 언어 레시피는 Node · Python · Go 만 있다. 그 밖의 언어(Java · Kotlin …)는 `recipe-common.md` · `recipe-ops.md` · `recipe-service.md` 만 적용하고, 언어 도구는 이름만 안내한다

## 5. 흔한 함정

| 함정 | 왜 문제인가 | 대신 |
|---|---|---|
| 커버리지 % 를 품질로 착각 | assertion 없는 테스트도 커버리지를 올린다 | 뮤테이션 스코어 병행 (80%+ 우수, 60% 미만 큰 공백) |
| Lighthouse 점수만 관리 | Lab 점수는 실사용자 경험이 아니다 | 필드 데이터(RUM) 병행, 절대 점수 대신 추세 |
| 자동 접근성 통과 = WCAG 준수 | 자동 도구는 이슈의 30 ~ 40% 만 잡는다 | 스크린리더 · 키보드 수동 테스트 |
| DORA 4 keys 만 추적 | 속도만 최적화하면 번아웃 | SPACE · DevEx 병행 |
| 도구 10개 동시 도입 | 알림 폭주 → 전원 무시 | 아픈 곳 하나부터, 2주 단위 |
| 완성도 = 기능 개수 | 기능은 많은데 아무도 안 쓴다 | 제품 분석으로 실사용 확인 |
| AI 생성 코드의 새 부채를 놓침 | 정적 분석은 프롬프트 · 데이터 · 출처 부채를 못 잡는다 | 프롬프트 버전 관리 · 생성 출처 기록 |

## 6. 이 플러그인이 하지 않는 것

| 하지 않는 것 | 이유 |
|---|---|
| 발견된 문제를 대신 고치기 | 설정과 게이트를 만들 뿐, 수정은 사람이 판단한다 |
| 점수를 올려주기 | 확인하지 못한 항목은 미통과로 둔다 |
| 디자인 심사 | 상태 처리 **누락**은 보지만 예쁜지는 보지 않는다 |
| 도구 가격 비교 | 가격은 빨리 낡는다. 추천은 레시피가 있는 도구로 한정한다 |
| 실시간 모니터링 | 무엇을 어떻게 잴지 알려줄 뿐 대시보드가 아니다 |
