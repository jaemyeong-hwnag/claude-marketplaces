# 서비스 건강도

규칙 원본: [`references/completeness-rules.md`](../../references/completeness-rules.md) — `Q-05` 있는가 ≠ 잘 되는가, `Q-06` 재지 않은 것은 미측정.

```bash
PC="${CLAUDE_PLUGIN_ROOT}/scripts/project-completeness.sh"
```

체크리스트는 장치가 **있는가**를 본다. 여기는 그 장치로 **잘 되는가**를 본다 — 온콜이 있어도 주 14번 깨우면 그 체계는 곧 무너진다.

## 1. 무엇을 잴지 보여준다

```bash
"$PC" health
```

지표 id · 단위 · 좋은 방향 · 최상 기준이 나온다. 사용자에게 **아는 값만** 달라고 한다.

## 2. 값을 모은다

| 출처 | 가져올 수 있는 것 |
|---|---|
| git · CI 기록 | `deploy_freq` (main 머지 · 배포 태그 수 / 주), `lead_time` (커밋 → 배포) — 저장소에 배포 기록이 있을 때만 계산한다 |
| 사용자 · 대시보드 | SLO · 에러버짓 · 인시던트 · 온콜 · 알림 · 포스트모템 · 소유자 · 롤백 시간 |

- 계산한 값은 **어떻게 계산했는지** 같이 적는다
- 사용자가 모르는 값은 비운다. 추정해 넣지 않는다 (`Q-06`)

## 3. 판정

```bash
"$PC" health cfr=8 recovery=45 pages_week=12 actionable_rate=18
```

단위는 `health` 목록의 단위 그대로 (%, 분, 시간, 건, 회/주). 모르는 지표 id · 숫자가 아닌 값은 멈춘다.

## 4. 보고

- 종합 판정과 **먼저 손볼 지표**(🟡 보통 이하)를 말한다
- **재지 않은 지표 수**를 같이 말한다 — 판정은 잰 것에 대해서만 유효하다
- DORA 는 2025 보고서부터 등급제가 아니다. 등급이 아니라 **방향**으로 말한다
- 나쁜 지표가 장치 부재 때문이면(롤백 시간이 길다 → `ops.rollback`) `completeness-apply` 로 그 항목을 제안한다

## 하지 않을 것

- 모르는 값을 업계 평균으로 채우기
- 지표 하나로 팀을 평가하기 — DORA 만 보면 속도만 최적화한다
