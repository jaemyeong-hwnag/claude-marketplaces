# 완성도 적용

규칙 원본: [`references/completeness-rules.md`](../../references/completeness-rules.md) — 적용 원칙 `Q-11` ~ `Q-19`, 게이트 단계, 축 순서, 레시피 형식.

```bash
PC="${CLAUDE_PLUGIN_ROOT}/scripts/project-completeness.sh"
```

## 1. 공백과 스택을 확정한다

- 이번 대화에 `completeness-review` 결과가 있으면 그것을 쓴다. 없으면 `"$PC" detect .` 로 이미 있는 것을 먼저 본다 — **있는 것을 다시 넣지 않는다**
- 스택 · 패키지 매니저는 매니페스트와 lockfile 로 확인한다 (레시피 머리말에 감지 순서가 있다)
- 공백이 여럿이면 **한 축만** 고른다. 사용자가 "전부" 라고 해도 축 순서대로 하나씩 하고 축마다 검증을 통과시킨다

## 2. 레시피를 가져온다

```bash
"$PC" recipe <항목 id>          # 그 항목을 메우는 레시피 전부
"$PC" recipe <이름>             # 이름으로 (gitleaks · knip …)
"$PC" recipe --list             # 파일 · 레시피 · 메우는 항목
```

레시피가 없으면 도구를 임의로 설정하지 않는다 (`Q-17`). 레시피 파일을 상대 경로로 찾지 않는다 — 대상 프로젝트가 아니라 플러그인 쪽에 있다.

## 3. 계획을 보여주고 동의를 받는다

파일을 건드리기 전에:

```
적용 대상: <축> — <항목 id …>
감지 스택: <언어> / <패키지 매니저> / CI <있음 · 없음>

  + <경로>        <무엇>
  ~ <경로>        <무엇을 더한다>
  $ <설치 명령>

게이트: 🟢 리포트만 → 안정화 뒤 차단 (시크릿 · Critical 취약점은 처음부터 차단)
롤백:   <되돌리는 방법>
```

이미 있는 파일은 바꿀 내용을 보여준다 (`Q-14`). CI 는 기존 워크플로에 job 을 더한다 — 파일을 늘리지 않는다.

## 4. 적용 → 검증

- 레시피의 설정을 그대로 쓰고 경로 · 패키지 매니저 · `<앱 주소>` 같은 자리만 맞춘다. `.gitignore` 추가 항목을 빠뜨리지 않는다
- 임계값은 **먼저 재고 그 값으로** 둔다 (`Q-13`)
- 레시피의 **검증** 명령을 실제로 돌린다

| 결과 | 조치 |
|---|---|
| 통과 | 보고로 |
| 설정 오류 | 고치고 다시 검증 |
| 코드에 실제 문제가 있어 실패 | 설정은 남기고 임계값을 현재 값으로 둔 뒤 문제를 보고한다 |
| 도구가 돌지 않는다 | 롤백하고 이유를 보고한다 |

CI YAML 을 고쳤으면 문법을 확인한다: `python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" <파일>`.
운영 레시피(관측성 · 알림)는 에러 없이 조용히 실패한다 — 트레이스 · 테스트 알림이 **실제로 닿는지** 본다.

## 5. 보고

```
적용 완료 — <축> (<항목 id …>)
변경: + <경로> · ~ <경로>
검증: $ <명령> → <결과>
현재 값: <측정값> (임계값을 여기에 고정 — 하락만 막는다)
발견한 문제: <있으면>
다음: <다음으로 비어 있는 축 하나>
커밋하지 않았습니다.
```

## 하지 않을 것

- 커밋 (`Q-16`) · 한 번에 도구 다섯 개 이상 켜기
- 자동 검사를 넣었다고 수동 항목(`ux.a11y-manual`)을 통과로 보고하기 (`Q-18`)
- 레거시 전체에 게이트 걸기 · AI 코드리뷰로 PR 차단 (`Q-19`)
- 검증 없이 "적용했습니다" 라고 보고하기
