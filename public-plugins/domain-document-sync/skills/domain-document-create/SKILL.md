# 도메인 문서 만들기

규칙 원본: [`references/domain-document-rules.md`](../../references/domain-document-rules.md)
골격: [`references/templates.md`](../../references/templates.md)

이미 있는 도메인의 내용을 고치는 것은 `domain-document-update` 다. 이 스킬은 **도메인을 새로 세운다.**

## 1. 범위

| 상황 | 범위 |
|---|---|
| 문서 루트(`docs/domain`)가 없다 | 저장소 전체 → 카탈로그부터 |
| 루트가 있고 도메인 하나를 더한다 | 그 도메인만 → 4절부터 |
| 기존 문서(README · wiki · ADR · 평면 `docs/*.md`)가 흩어져 있다 | 전체. 기존 문서는 재료로 쓰고, 옮긴 뒤 원본을 어떻게 할지 사용자에게 묻는다 |

## 2. 코드베이스를 읽는다 — 언어를 가정하지 않는다

먼저 무엇으로 만든 저장소인지 신호로 판단한다. 한 저장소에 여럿이 섞여도 된다.

| 신호 | 어디서 |
|---|---|
| 빌드 · 패키지 | `package.json` · `pom.xml` · `build.gradle*` · `go.mod` · `pyproject.toml` · `Cargo.toml` · `composer.json` · `Gemfile` · `*.csproj` · `mix.exs` … |
| 모듈 경계 | 모노레포 워크스페이스 · 멀티 모듈 · `apps/` `packages/` `services/` `modules/` `features/` `domain/` |
| 데이터 | 마이그레이션 · ORM 모델 · 엔티티 · `schema.prisma` · `*.sql` · 스키마 파일 |
| 외부 계약 | 라우트 · 컨트롤러 · 핸들러 · OpenAPI · GraphQL · protobuf · 이벤트 · 큐 컨슈머 · CLI 명령 |
| 사람의 말 | README · 기존 문서 · 화면 문구 · 이슈 · 커밋 메시지의 반복 명사 |

큰 저장소는 모듈 · 서비스 단위로 서브에이전트를 나눠 병렬로 읽고 결과(명사 · 데이터 · 계약 · 경로)만 모은다.

## 3. 도메인을 나눈다

**기술 계층이 아니라 업무 개념으로** 나눈다. `controller` · `service` · `utils` 는 도메인이 아니다.

도메인 하나는 대개 이것들이 함께 모이는 곳이다.

- 업무에서 부르는 명사 하나 (주문 · 정산 · 회원 · 재고)
- 그 명사가 소유하는 데이터 (테이블 · 컬렉션 · 모델)와 상태값
- 그 데이터를 바꾸는 흐름과 외부 계약

| 판단 | 기준 |
|---|---|
| 합친다 | 두 후보가 같은 데이터를 같이 바꾸고, 따로 설명하면 반복이 많다 |
| 나눈다 | 바뀌는 이유 · 담당자 · 용어가 다르다. 한 쪽만 고치는 작업이 흔하다 |
| 공통 도메인 | 여러 도메인이 기대는 규약(이력 · 권한 · 코드값)은 따로 세우고 관계로 잇는다 |
| 크기 | concept 몇 개(합쳐 수백 ~ 천 줄)에 들어가면 적당. 한 줄로 못 말하면 너무 크다 |

후보마다 정한다: slug(영문 kebab-case, 코드에서 부르는 이름) · 한 줄 · `code:` 글롭 · 관계 · 파트 목록.

**후보 표를 사용자에게 먼저 보여준다** — 도메인 경계는 되돌리기 비싸다. 도메인 하나를 더하는 경우는 바로 진행한다.

## 4. 쓴다 — 아래에서 위로

도메인마다:

1. **concept** — "언제 보는가" 로 파트를 나눈다 (templates.md "concept 을 어떻게 나누나"). 코드에서 확인한 사실만, 위치(파일 · 심볼)와 함께. 모르는 것은 "확인 필요"
2. **`_meta.md`** — 프런트매터 `code:` 글롭 · 한 줄 · 위치 · 관계 · 파트 표. 작은 도메인은 본문을 여기 바로 쓰고 concept 을 만들지 않는다
3. **`_index.md`** — 1행. 트리거를 네 갈래(말 · 식별자 · 경로 · 증상)로 채운다. 식별자 · 경로는 2절에서 모은 실제 이름을 그대로

전부 쓴 뒤 두 도메인에 걸리는 키워드를 모아 `_index.md` "겹칠 때" 표를 만든다.

`code:` 는 좁게 쓴다. 테스트 · 생성 코드는 `!` 로 뺀다. 코드가 없는 도메인(정책 · 용어)은 `code:` 를 두지 않는다.

## 5. 확인

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/domain-document-sync.sh" map .        # 도메인마다 걸리는 파일 수 — 0 이나 과다는 글롭을 고친다
"${CLAUDE_PLUGIN_ROOT}/scripts/domain-document-sync.sh" validate .   # D-01 ~ D-08
```

- `map` 에서 어느 도메인에도 안 걸리는 주요 코드 디렉터리가 있으면 도메인이 빠졌거나 글롭이 좁다
- `validate` 에 `❌` 가 없어야 끝이다
- 문서 루트를 `docs/domain` 이 아닌 곳에 뒀으면 프로젝트 `.claude/settings.json` 의 `env.DOMAIN_DOCUMENT_ROOT` 에 적는다

## 하지 않을 것

- 코드를 읽지 않고 이름만 보고 문서를 쓰지 않는다
- 모든 클래스 · 파일을 나열하지 않는다. 문서는 "왜 · 규칙 · 흐름" 이다 — 목록은 코드가 더 정확하다
- 프로젝트 전용 규약(이 플러그인이 모르는 것)을 이 플러그인 파일에 적지 않는다. 대상 저장소의 문서에 쓴다
