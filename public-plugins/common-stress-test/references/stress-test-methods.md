# 스트레스 테스트 정량 측정 — 이론과 근거

규칙은 [`stress-test-rules.md`](stress-test-rules.md) 에 있다. 이 문서는 그 규칙이 기대는 **식과 연구 결과**를 모은다.
수치는 원문으로 확인한 것만 적었다. "(유도)" 는 원문 식에서 대수로 끌어낸 것이다.

## 1. Little's Law — 측정이 맞는지 보는 항등식

- **L = λW**
  - L: 시스템 안 평균 요청 수
  - λ: 처리율
  - W: 평균 체류 시간
- Little(Operations Research 2011)의 Theorem LL.1: 관측 구간의 시작과 끝에 시스템이 비어 있으면 L = λW 가 **정확히** 성립한다.
  - 정상 상태일 필요가 없다.
  - 큐 규율(FIFO · LIFO · 우선순위)과 무관하다.
- closed 부하에서는 루프 전체에 적용한다. **N = X·(R + Z)** (유도)
  - N: VU 수
  - X: 처리량
  - R: 응답시간
  - Z: think time

**쓰는 법**
1. 단계마다 서버 in-flight 평균과 X·W 를 비교한다.
2. 어긋나면 측정 경계를 의심한다. 예: LB 대기가 빠졌다, 에러가 집계에서 빠졌다, 램프 구간이 섞였다.
3. 목표 처리량 × 목표 응답시간으로 필요한 동시성(스레드 · 커넥션 풀 하한)을 바로 구한다.

## 2. USL — 동시성에 따른 처리량 모델 (Gunther)

**모델**

```
X(N) = γN / (1 + α(N−1) + βN(N−1))
N_max = √((1−α)/β)
```

| 계수 | 뜻 | 원인 예 |
|---|---|---|
| α | 경합 — 직렬화 비용 | 락 · 단일 스레드 구간 · 공유 큐 |
| β | 일관성 비용 | 캐시 무효화 · 분산 락 |
| γ | X(1) | 동시성 1일 때 처리량 |

- β > 0 이면 N_max 를 넘는 동시성에서 처리량이 **줄어든다**.
- β = 0 이면 Amdahl 법칙이 되고, 처리량은 X(1)/α 에 수렴한다.

**측정과 피팅**
- Gunther 는 정상 상태 측정점 6개 이상을 권한다.
- 선형화하면 N/C(N) − 1 = α(N−1) + βN(N−1) 이다 (C = X/X(1), 유도).
  - `stress-report-generate.sh` 는 이 식을 최소제곱으로 풀어 시작점을 잡는다.
  - 그다음 처리량 공간의 제곱오차를 줄이도록 다듬는다 (α, β ≥ 0).
  - 검증: α 0.05 · β 0.001 로 만든 데이터(±1% 잡음)에서 α 0.0503 · β 0.000994 · N_max 30.9 (참값 30.8) 를 되찾았다.
- R² 가 낮으면 USL 모양이 아닌 병목이다. 예: 고정 풀 크기 같은 딱딱한 상한.
  - **실측**: 동시 처리 4개로 제한한 서버는 R² 0.84 였다. 이때는 knee(N = 4)가 더 정확했다.

## 3. 포화점 — knee

**M/M/1 응답시간**
- R = S/(1−ρ). 이용률 ρ → 1 이면 발산한다.
- p 분위 응답시간 = −ln(1−p)/(μ−λ) (유도). 예: p99 ≈ 4.6/(μ−λ).

**Millsap 의 knee**
- R/ρ 를 최소로 만드는 이용률이다.
- M/M/m 기준값 (저자 발표 자료로만 확인):

| 서버 수 m | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 |
|---|---|---|---|---|---|---|---|---|
| knee 이용률 | 50% | 57% | 66% | 74% | 81% | 86% | 89% | 92% |

- Gunther 의 반론: knee 는 없고 SLA 만 있다. 그래서 운영 상한은 SLO 를 넘지 않는 지속 가능 용량과 **같이** 본다.

**Kneedle** (Satopää et al., ICDCS Workshops 2011)
1. 곡선을 단위 정사각형으로 정규화한다.
2. 차이 곡선의 최대점을 knee 로 잡는다.
   - 처리량(증가 후 꺾임): y − x
   - 지연(볼록): x − y
- 오프라인 데이터에서는 민감도 S = 0 이 가장 좋았다.
- **실측**: 용량 200 rps 서버의 knee 가 180 rps 로 나왔다. 처리량 곡선과 p99 곡선이 같은 점을 가리켰다.

## 4. open · closed 모델과 coordinated omission

**모델 비교** — Schroeder · Wierman · Harchol-Balter (NSDI 2006)
- 같은 부하에서 closed 의 응답시간이 open 보다 현저히 낮다. 한 자릿수 이상 차이 날 수 있다.
- MPL 1000 에서도 차이가 남는다.
- partly-open 은 세션당 요청이 5개 이하이면 open, 10개 이상이면 closed 처럼 움직인다.

**coordinated omission** — Tene 2013 · wrk2 · HdrHistogram
- 부하기가 서버 정지 동안 요청을 보내지 않아 나쁜 구간의 표본이 빠지는 현상이다.
- Tene 의 예시: 100 req/s · 1 ms 서버가 100초 멈추면 순진한 측정은 p99.99 = 1 ms 를 보고한다. 올바른 값은 약 100 s 다.
- 대책:
  1. 도착률을 고정하는 부하기를 쓴다.
  2. 지연을 "보냈어야 할 시각"부터 잰다 (wrk2).
  3. 사후 보정한다 (`copyCorrectedForCoordinatedOmission`). 단, 기록 시점 보정과 같이 쓰지 않는다.
- wrk2 는 10 ~ 20초보다 짧은 실행이 의미 없을 수 있다고 적었다.

**실측** — 10초마다 2초 멈추는 서버를 40초 측정했다.

| 모델 | 요청 수 | avg | p90 | p99 | max |
|---|---|---|---|---|---|
| closed 1 VU | 2,653 | 5.2 ms | 2 ms | **4 ms** | 2,004 ms |
| open 100 rps | 3,857 | 191.5 ms | 976 ms | **1,913 ms** | 2,011 ms |

max 는 둘 다 정지를 봤지만, closed 는 정지 동안 요청을 거의 보내지 않아 분위수에 드러나지 않았다.

## 5. 꼬리 지연 — The Tail at Scale (Dean & Barroso, CACM 2013)

- fan-out 이 꼬리를 키운다.
  - 서버 p99 가 1 s 일 때 100대에 fan-out 하면 요청의 63% 가 1 s 를 넘는다 (1 − 0.99¹⁰⁰).
  - leaf 하나는 p99 10 ms 인데, 전체 leaf 완료를 기다리는 루트 p99 는 140 ms 였다.
- hedged request 를 10 ms 뒤에 보내자 p99.9 가 1,800 ms → 74 ms 로 줄었다. 추가 요청은 2% 였다.
- 하위 호출 k 개의 p 분위가 상위로 증폭되는 정도는 **1 − (1 − p)^k** 로 역산한다 (유도).

## 6. 분위수 집계

**합치는 법**
- 미리 계산한 분위수를 평균 내지 않는다. Prometheus 문서가 `avg(...{quantile="0.95"})` 를 나쁜 예로 든다.
- 히스토그램 버킷을 합친 뒤 분위수를 한 번 계산한다.
  - `histogram_quantile(0.99, sum by (le) (rate(x_bucket[5m])))`
- 부하기 여러 대의 결과도 같다. p99 끼리 평균 내지 않고 원자료나 히스토그램을 합친다.

**버킷 해상도**
- 버킷이 거칠면 오차가 생긴다. 실제 값이 220 ms 에 몰려 있을 때 거친 버킷은 p95 를 295 ms 로 추정했다.
- SLO 경계값을 버킷 경계로 둔다.

**자료 구조 선택**

| 구조 | 오차 · 병합 |
|---|---|
| HdrHistogram | 유효 자릿수 3이면 오차 0.1% 이하 |
| DDSketch (PVLDB 2019) | 상대오차 α 를 보장하고 완전 병합된다 |
| t-digest | 꼬리 정확도가 높지만 rank 오차 기반이라 heavy-tail 에서 상대오차가 커질 수 있다 |

**평균 · 표준편차** — 지연 분포를 요약하지 못한다. Tene: "standard deviation and application latency should never show up on the same page".

## 7. 신호 — 어디가 병목인가

| 방법 | 대상 | 신호 |
|---|---|---|
| RED (Wilkie) | 서비스 | Rate · Errors · Duration |
| USE (Gregg) | 자원마다 | Utilization · Saturation(대기열) · Errors |
| Golden Signals (Google SRE 6장) | 서비스 | Latency(성공 · 실패 구분) · Traffic · Errors · Saturation |

- 부하기 쪽은 RED 로 SLO 위반 지점을 찾는다.
- 같은 시각의 서버 USE 로 원인 자원을 찾는다.
- 자원 지표는 초 단위로 모은다. 5분 평균 CPU 80% 안에 수 초짜리 100% 가 숨는다 (Gregg).

## 8. 비교 · 회귀의 통계

| 근거 | 내용 |
|---|---|
| Georges et al., OOPSLA 2007 | 평균 차이의 신뢰구간이 0 을 포함하면 차이가 없다. 흔한 방식(최솟값 · 중앙값 한 번)은 차이 1% 를 판정할 때 20% 넘게 틀렸다. steady state 는 최근 k 회의 CoV 가 0.01 ~ 0.02 아래일 때. 신뢰구간이 평균의 1 ~ 2% 안이거나 30 회면 멈춘다 |
| Kalibera & Jones, ISMM 2013 | 수준(빌드 · 실행 · 반복)마다 반복 수를 정한다. "A 가 B 보다 5.5% ± 2.5% 빠르다" 처럼 효과 크기 신뢰구간으로 보고한다. 2011년 논문 90편 중 71편이 변동을 보고하지 않았다 |
| Arcuri & Briand, ICSE 2011 | Mann-Whitney U + 효과 크기(Vargha-Delaney Â₁₂). p 는 유의 여부와 상관없이 보고한다 |
| Romano et al. 2006 | Cliff's delta: 0.147 · 0.33 · 0.474 경계 |
| Laaber et al., EMSE 2019 | 클라우드 마이크로벤치마크 CoV 0.03% ~ 100% 이상. 같은 인스턴스에서 번갈아 무작위 순서로 돌리면 인스턴스 10대 이상에서 모든 감속을 탐지했다. Wilcoxon 이 bootstrap 보다 작은 감속을 잡았다 |
| Bulej et al. (Duet), ICPE 2020 | 두 버전을 같은 머신에서 동시에 돌리면 정확도가 평균 5 ~ 37배 좋아졌다 |
| Barrett et al., OOPSLA 2017 | ⟨VM, 벤치마크⟩ 의 30.0 ~ 43.5% 만 일관되게 최고 성능 steady state 에 도달했다 |
| Traini et al., EMSE 2023 | JMH 벤치 586개 중 43.5% 가 실행마다 steady state 도달이 엇갈렸다. 개발자가 정한 워밍업은 19% 만 맞았다 |
| Nguyen et al., ICPE 2012 | 관리도의 위반 비율로 회귀를 탐지했다 (정밀도 75% · 재현율 100%). 부하 차이를 보정하면 실행 간 차이가 20% → 9% 로 줄었다 |
| Daly et al., ICPE 2020 (MongoDB) | 고정 10% 임계는 거짓 양성이 최대 99% 였다. E-Divisive 변화점 탐지로 바꿨다 |
| Fleming et al. (Hunter), ICPE 2023 | 변화점 탐지의 순열 검정을 t 검정으로 바꿔 결과를 결정적으로 만들었다 |

`stress-regression-validate.sh` 의 U · p · delta 는 scipy `mannwhitneyu` 와 네 경우(정확 · 동률 · 정규 근사)에서 소수점 넷째 자리까지 같았다.

## 9. 유형별 측정 설계 (k6 문서 · ISTQB)

| 유형 | 부하 형태 | 판정 |
|---|---|---|
| load | 평균 부하를 유지한다 | SLO |
| stress | 평균보다 높은 부하. 고정 비율은 없다 (문서 예시는 +50 ~ 100%) | 평균 대비 저하 |
| spike | 짧은 램프 → 유지 없음 · 짧음 → 빠른 하강 | 정상 상태로 돌아오기까지 걸린 시간 |
| soak | 평균 부하를 3 ~ 72시간 | 지연 증가 · 메모리 기울기 · 저장소 |
| breakpoint | `ramping-arrival-rate` 로 실패할 때까지. 오토스케일을 끈다 | 지속 가능 용량 · knee |

**누수 판정** (Jindal et al. 2021)
1. 메모리 시계열의 끝에서부터 선형회귀를 한다.
2. 결정계수가 기준 이상이고, 추세선이 한계에 닿는 시간이 기준 이내이면 누수로 본다.

## 10. 운영 프로파일과 도메인 지표

- 부하는 운영 로그에서 뽑는다.
  - WESSBAS (Vögele et al., SoSyM 2018): 세션 로그를 마르코프 모델로 바꾼 뒤 부하 스크립트로 만든다.
- 결과를 운영 발생 확률로 가중해 0 ~ 1 점수로 만든다 (Avritzer et al., ECSA 2018).
  - D = Σ p(λᵢ)·ŝᵢ
  - 각 서비스의 통과 기준은 무부하 기준 실행의 평균 + 3σ 다.
