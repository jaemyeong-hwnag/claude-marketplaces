# 성능 리뷰

규칙 원본: [`references/performance-rules.md`](../../references/performance-rules.md)
근거: [`references/performance-methods.md`](../../references/performance-methods.md)

패턴은 스크립트가 찾는다. 이 스킬은 **그것이 정말 문제인지, 얼마나 큰지, 어떻게 확인할지**를 정한다.

## 1. 범위를 정한다

| 요청 | 대상 |
|---|---|
| 지금 작업 · 브랜치 · PR | 기본 브랜치 대비 변경 — `git diff $(git merge-base HEAD origin/HEAD)` |
| 파일 · 디렉터리를 지정 | 그 경로 전체 |

변경된 함수의 **호출자와 데이터 출처**까지 읽는다. diff 만 보고 판정하지 않는다 (`PF-44`).

## 2. 기계 패턴을 먼저 돌린다

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/performance-validate.sh" --diff          # 변경된 줄만
"${CLAUDE_PLUGIN_ROOT}/scripts/performance-validate.sh" src/              # 경로 전체
```

결과는 후보 목록이다. 하나씩 맥락을 읽고 `확정` · `오탐` 을 가른다. 프로젝트에 린터가 있으면 성능 규칙 결과도 같이 본다 (SpotBugs · PMD · Ruff `PERF` · `ASYNC` · staticcheck `SA6` · Biome `performance` — 매핑은 근거 문서 3절).

## 3. 9개 범주를 모두 판정한다

패턴에 안 걸린 것이 더 많다. 범주마다 코드를 읽고 `발견` · `문제없음` · `해당없음` · `측정필요` 를 낸다 (`PF-30` ~ `PF-38`). **빈 범주가 있으면 끝나지 않은 것이다.**

| 범주 | 패턴이 못 보는 것 — 직접 찾는다 |
|---|---|
| 시간 복잡도 | 변경 전후 Big-O 증가, 여러 함수에 걸친 중첩 반복, 반복 정렬 · 재계산 |
| 공간 · 할당 | 요청마다 전체를 메모리에 올림, 무한히 자라는 구조, 큰 값 복사 |
| DB 쿼리 | 지연 로딩 연관 접근(`order.getCustomer()` · `entry.blog.name`)이 루프 · 직렬화 안에서 일어남, 새 WHERE · ORDER BY 컬럼의 인덱스, 트랜잭션 범위 |
| 네트워크 · IO | 다른 함수를 거쳐 루프 안에서 일어나는 호출, 재시도 층 중복, 데드라인 미전파, 트랜잭션 안 외부 호출 |
| 동시성 · 락 | 락 안의 IO, 락 순서, 풀 · 큐 크기 근거, 팬아웃 |
| 캐싱 | 무효화 없는 캐시, 동시 미스, 캐시 키 폭발 |
| 페이로드 · 용량 | 요청 파라미터로 크기가 정해지는 응답 · 조회, 업로드 상한 |
| 자원 해제 | 예외 경로에서 닫히지 않는 커넥션 · 스트림 · 응답 바디 |
| 정규식 | 사용자 입력이 닿는 패턴 |

## 4. 지적을 쓴다

```
[DB 쿼리/PF-01] 심각도 높음 · 신뢰도 높음
위치: OrderService.kt:42
근거: for (o in orders) 안에서 o.customer 지연 로딩 → 쿼리 1+N
규모 가정: 페이지당 50건 → 요청당 51 쿼리
수정: @EntityGraph(attributePaths = ["customer"]) — 순서 · 결과 동일
검증: 쿼리 수 assert (주문 50건과 100건에서 쿼리 수가 같아야 한다)
```

- 규모 가정이 없으면 `낮음` 보다 올리지 않는다 (`PF-41`)
- 런타임 · 데이터 분포에 달린 것은 `측정필요` 로 두고 검증 방법을 적는다 (`PF-42`)
- 원래 있던 문제는 이번 변경의 지적과 나눠 적는다 (`PF-43`)
- 마이크로 최적화는 측정 근거가 없으면 `낮음` 이다 (`PF-45`)
- 캐시는 반복 계산의 근거와 무효화 조건이 있을 때만 제안한다 (`PF-47`)

## 5. 보고한다

1. 범주 9개의 판정 표 — 범주 · 판정 · 한 줄 이유
2. 지적 목록 — 심각도 높은 것부터
3. `측정필요` 의 검증 계획 — 쿼리 수 assert · `EXPLAIN` · 벤치마크 · 부하 테스트 중 무엇을 어떻게 (규칙 원본 4절)
4. 오탐으로 판단한 패턴 — 이유와 함께. `performance-ignore` 주석은 사용자가 원할 때만 넣는다

고치자고 하면 지적 하나씩 고치고, 검증 방법대로 테스트를 더한 뒤 `performance-validate.sh` 를 다시 돌린다.

## 하지 않을 것

- 측정 없이 "N% 빨라진다" 고 단정하지 않는다
- 패턴에 걸렸다는 이유만으로 지적하지 않는다 — 맥락을 읽고 판정한다
- 기능 동등성을 확인하지 않은 최적화를 제안하지 않는다 (`PF-46`)
- 스스로 `performance-ignore` 주석을 넣어 경고를 없애지 않는다
